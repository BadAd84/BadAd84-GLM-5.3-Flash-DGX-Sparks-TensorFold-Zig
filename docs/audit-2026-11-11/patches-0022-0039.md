## 2. Ranked REGRESSION, intended-flip and unclear items

### Default path

**R1. 0029: `attendLastRow` launches the sparse pass over `rows` rows instead of 1.**
- Pin (`cuda_dsa_block.zig:211`): one row, with the scratch already advanced to the last row (`v.qa`, `v.ol` offset by `r0 = rows - 1`, pin :186-189).
- Parity (:230): the same advanced scratch, but `rows` rows. It reads queries `r0 .. r0 + rows - 1`, uses token lists for rows 1 and up that this call never selected (`selectTokensProfile` ran for 1 row, :225), and writes `ol` rows `r0 .. 2*r0`, which is `rows - 1` rows past the chunk's buffer.
- When: a prompt MTP chunk (`blockLastRow`, parity :182-198) with more than one row once `sparseRows` is true, that is positions past the dense limit. No knob is involved.
- The `onepass.run(..., rows, ...)` hook above it (:227-229) carries the same `rows`, but is dead today (it needs `set.onepass`, see K1).
- Fix: change `rows` to `1` at parity :230, the pin's line. AuditPatches09to21 reports the same line under 0016, which introduced the `rows` copy; 0029 deleted the wrong one of the two.

**R2. 0023: a second `own.lanes = ...` overwrites the pin's.**
- Parity `cuda_native.zig:360` is the pin's line (pin :353). Line :361 assigns again without `.mtp_confidence` and with `.together = !off("TF_GLM_PROMPT_MANY")`.
- Effect (a), concurrency: `together` is true, so `backend()` (`cuda_lanes.zig:81`) returns `steps_many_vt` (:108-113, `prefill_many = prefillManyFn`, `many_rows = 2048`). The pin's stepped vtable has `prefill_many = null`, `many_rows = 0` (pin :86-92). Two or more short text prompts admitted together now run one batched `prefillMany` pass (`core/lanes/open.zig:44-60`, `core/lane_host_admit.zig:60-63, 88`); the pin fills each by steps. `prefillManyFn` declines when not tiled or when `TF_KV_SHARE` is on (`cuda_lanes.zig:243`).
- Effect (b): `--mtp-confidence` is silently ignored. `lanes.mtp_confidence` stays null, so `draft_confidence` is null (:134), no chances are requested (:505) and `chancesFn` returns false without a drafter (:555). This bites only with the MTP head and no DFlash drafter.
- The patch text says the pin's paths run unchanged; with `together` defaulting true they do not.
- Fix: delete :361; keep the pin's line and set `together` and `multi` from OVN knobs that default off (for example `own.lanes.together = own.lanes.multi or cuda.ovn.on("PROMPT_MANY")`), and make the field default false.

**R3. 0031: the pin's head-block rule is replaced by the era's.**
- Pin: `headBlock(rows)` is 32 heads from 64 rows, else 16 (`cuda_latent.zig:16-17`), used at pin `cuda_latent.zig:118` and `cuda_dsa_block.zig:203, 217`.
- Parity: `headBlockOf(rows, heads)` (:21-24) also returns 32 when `rows >= 5` and heads are 17 to 24.
- When: TP=3 only (22/21/21 heads a rank), launches of 5 to 63 rows: decode windows, shared rounds, short prompt chunks. They take `chunks_32*` with a `cdiv(heads, 32)` grid instead of `chunks_16*`.
- The patch says "the port had flattened it"; in fact the rows-only rule is the pin's own, and the change was made so an OVN test from 0021 passes.
- **Unclear:** whether the output bits change. Partials are passed by row and head, and `docs/BENCH.md` records knobs-off as bit-exact to stock at TP=3, but I did not read the `chunks_16`/`chunks_32` kernels. A digest comparison against the pin at TP=3 on a 5 to 8 row window settles it.
- Fix: restore `headBlock(rows)` at the three sites and put `headBlockOf` behind a default-off knob.

**R4. 0024: `try s.synchronize();` dropped before the packing download.**
- Pin `cuda_tile.zig:175-176`: synchronise the load stream, then read the linear back. Parity :181 reads it back directly.
- When: load time with `TF_GLM_DENSE_BITS` or `TF_GLM_HEAD_BITS` other than 16. A preceding 16-bit iteration leaves an async copy from `tmp` pending (parity :176-178), and the next packed iteration reuses `tmp` (:186-187).
- **Unclear:** whether it is observable. The stream is created blocking (`cuda_engine.zig:142`, `Stream.init(d, false)`), and a synchronous `cuMemcpyDtoH` normally waits for blocking streams, so the pin's call may be redundant. That is inference about the driver, not something I read in the tree.
- Fix: put the line back before parity :181.

**R5. 0022: L2PF join moved and re-gated.**
- Pin `cuda_forward.zig:490-491`: `streamMean`, then join only for a single-rank decode window (`pf`). Parity :479-480: join whenever `f.l2pf` is set, before `streamMean`.
- When: `TF_GLM_L2PF` is on by default on a GB10 at two or more ranks (`cuda_l2pf.zig:48-50`), so this is the fleet's default path. Decode windows now make `streamMean` wait on the side stream; prompt chunks through `whole()` gain a join on an idle side stream. The prefetch only reads, so this is timing only.
- The same hunk adds a dead `fn prefetch(f, j, which)` (parity :483-487) calling `p.site`, which the pin's `L2pf` does not have (`cuda_l2pf.zig:160-240`). It compiles only because nothing calls it.
- Fix: restore pin :490-491 and delete the dead function.

**I1. 0018, 0026, 0027: `allocate_shared_drafts` default flipped (intended).**
- Pin :101 sets it to `drafting`; parity `cuda_lanes.zig:140` sets it only with `SHARED_DRAFTS`.
- When: every shared round (two or more streams) with all knobs off uses the depth rule, where the pin uses the core allocator.
- 0027 states the flip and cites `docs/PARITY.md`, and edits the pin's `copy_drafts_cuda_test` literal to match. 0018's text calls the depth rule "the pin's behaviour today", which the pin's line contradicts.
- Decision for the owner: accept as a recorded deviation, or invert the knob so off equals the pin.

### Knob-on only

**K1. 0022: `Forward.set()` no longer passes `.onepass`, `.onepass_pipe`, `.mla`.**
